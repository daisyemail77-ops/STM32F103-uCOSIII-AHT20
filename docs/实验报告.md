## 3 任务一：uC/OS-III 的移植与三任务设计

### 3.1 RTOS 与 uC/OS-III

裸机程序是“一个大循环 + 中断”，所有功能串行执行，长延时（如 `HAL_Delay(2000)`）期间 CPU 空转，其他功能得不到响应。RTOS 把功能拆成多个独立任务，由内核按优先级调度，用系统节拍（Tick）驱动延时和超时，延时期间 CPU 去运行其他任务。

uC/OS-III 是一个可裁剪、可剥夺的实时内核，主要特性：

- 任务优先级 0～63（可配置），数值越小优先级越高；
- 每个任务有独立的栈和 TCB（任务控制块）；
- 支持信号量、互斥量、消息队列、事件标志、软件定时器；
- 上下文切换由 PendSV 异常完成，系统节拍由 SysTick 产生；
- 源码开放（V3.08 起为 Apache-2.0），适合学习移植。

### 3.2 移植原理（Cortex-M3）

Cortex-M3 有两个栈指针：MSP（主栈，中断使用）和 PSP（进程栈，任务使用）。uC/OS-III 的移植层需要完成四件事：

1. **任务栈初始化** `OSTaskStkInit()`：按异常入栈帧格式（R0-R3、R12、LR、PC、xPSR）构造初始栈，使任务第一次被调度时能“从中断返回”进入任务函数。
2. **上下文切换** `OSCtxSw()` / `OS_CPU_PendSVHandler()`：挂起 PendSV，在 PendSV 中保存 R4-R11 到任务栈、切换 `OSTCBCurPtr`、恢复新任务的 R4-R11 和 PSP。
3. **系统节拍** `OS_CPU_SysTickHandler()`：调用 `OSIntEnter()` → `OSTimeTick()` → `OSIntExit()`，为延时、超时、时间片提供时基。
4. **临界区** `CPU_SR_Save()/Restore()`：用 `PRIMASK`/`BASEPRI` 关中断，配合 `CPU_CFG_KA_IPL_BOUNDARY` 区分“内核感知”和“非内核感知”中断。

PendSV 必须设为最低优先级（0xFF），保证上下文切换不会打断其他中断；SysTick 设为内核边界优先级（本实验为 4）。

## 4 任务二：I2C 总线与 AHT20 采集

### 4.1 I2C 协议要点

I2C 是两线制同步串行总线：SCL（时钟）和 SDA（数据），均为开漏输出，需外接上拉电阻（模块一般自带 4.7 kΩ）。

一次写传输的帧格式：

```
START → 7 位地址 + W(0) → ACK → 数据字节 → ACK → ... → STOP
```

一次读传输：

```
START → 7 位地址 + R(1) → ACK → 数据字节 → ACK/NACK → ... → STOP
```

- 起始条件：SCL 高电平期间 SDA 由高变低；
- 停止条件：SCL 高电平期间 SDA 由低变高；
- 数据在 SCL 低电平期间改变，在 SCL 高电平期间采样；
- 第 9 个时钟为应答位：从机拉低 SDA 表示 ACK，释放为 NACK；
- 标准模式 100 kHz，快速模式 400 kHz。本实验用 400 kHz，SCL 周期 2.5 μs。

### 4.2 软件 I2C 与硬件 I2C（任务二 1））

**硬件 I2C**：STM32 片内集成 I2C 外设，起始/停止条件、时钟产生、数据移位、ACK、仲裁和错误检测（BERR、ARLO、AF、OVR）全部由硬件完成。CPU 只需配置寄存器并通过 `HAL_I2C_Master_Transmit/Receive` 读写数据寄存器，可配合中断/DMA。优点是速度快（100 k/400 k/1 M）、CPU 占用低、时序精确；缺点是引脚固定（I2C1 默认 PB6/PB7，重映射 PB8/PB9），且 STM32F1 的 I2C 外设存在已知 errata（BUSY 标志卡死、总线锁死），调试时容易卡在 `HAL_BUSY` 或超时。

**软件 I2C**：用两个 GPIO（开漏输出）通过软件延时模拟 SCL/SDA 时序，逐位发送和采样。优点是引脚任意、移植方便、逻辑直观、便于示波器观察；缺点是占用 CPU、速率低（一般 50～100 kHz）、时序会被中断或任务切换打断（RTOS 中需关调度或用临界区保护），并且依赖上拉电阻。

**野火教材第 23 章（I2C 读写 EEPROM）**：以 AT24C02 为例，分别给出硬件 I2C 和软件模拟 I2C 两套读写例程；硬件 I2C 用 STM32 的 I2C 外设产生时序，软件 I2C 用 GPIO 翻转模拟时序；两者在时序、代码量、移植性和稳定性上各有取舍，实际工程中低速率、多从机、引脚受限时常用软件 I2C，高速率、总线复杂时用硬件 I2C。

本实验采用**硬件 I2C1（PB6/PB7，400 kHz）**。

### 4.3 AHT20 数据手册要点

- 供电 2.2～5.5 V，I2C 接口，7 位地址 **0x38**（写 0x70，读 0x71）；
- 上电后至少等待 40 ms 再通信；
- 状态字节：bit7 = 忙，bit3 = 已校准；
- 初始化/校准命令：`0xBE 0x08 0x00`；
- 触发测量命令：`0xAC 0x33 0x00`，测量时间典型 80 ms；
- 测量完成后读 6 字节：`[状态][湿度高8位][湿度中8位][湿度低4位|温度高4位][温度中8位][温度低8位]`（第 7 字节为 CRC，可省略）；
- 数据换算（20 位）：

```
raw_h = (d[1]<<12) | (d[2]<<4) | (d[3]>>4)      RH  = raw_h / 2^20 × 100 %
raw_t = ((d[3]&0x0F)<<16) | (d[4]<<8) | d[5]   T   = raw_t / 2^20 × 200 − 50 ℃
```

程序用定点运算输出一位小数：`RH×10 = raw_h×1000/2^20`，`T×10 = raw_t×2000/2^20 − 500`。

### 4.5 RTOS 版任务 3（任务二 3)）

在任务一工程中把 `app_tasks.h` 的 `APP_TASK3_USE_AHT20` 改为 1，任务 3 变成：

```c
static void AppTaskAHT20(void *p_arg)
{
    AHT20_Init(&hi2c1);
    while (1) {
        AHT20_ReadData(&hi2c1, &temp10, &humi10);
        printf("Temp: %d.%d C, Humi: %d.%d %%RH\r\n", ...);
        OSTimeDlyHMSM(0u, 0u, 2u, 0u, OS_OPT_TIME_HMSM_STRICT, &err);
```

AHT20 驱动内部等待 80 ms 的 `AHT20_DelayMs()` 被重定向到 `OSTimeDlyHMSM`，等待期间 CPU 去运行 LED 任务；若直接用 `HAL_Delay`，虽然高优先级任务仍能靠 SysTick 抢占，但低优先级任务会被拖住。

### 4.6 示波器观察 I2C 时序（任务二 4)）

**测量方法**：探头 CH1 接 PB6（SCL），CH2 接 PB7（SDA），共地；触发源选 SCL 下降沿，时基 5～10 μs/div；用 I2C 解码功能可直接读出地址和数据。

**观察到的时序（写初始化命令）**：

```
START: SCL 高，SDA 由高→低
地址字节: 0x70 (0111 0000)  —— 7 位地址 0x38 左移一位，最低位 0 表示写
第 9 个时钟: SDA 被从机拉低 = ACK
数据: 0xBE 0x08 0x00，每个字节后都有 ACK
STOP: SCL 高，SDA 由低→高
```

随后是状态读取（地址 0x71，读 1 字节），再发测量命令 `0xAC 0x33 0x00`，等 80 ms 后读 6 字节。

**回答手册问题**：

- 模块在初始化阶段的 I2C 地址是 **0x38（7 位）**，程序中写作 `0x38 << 1 = 0x70`（写）/ `0x71`（读）；
- 程序先发送 **0xBE 0x08 0x00**（校准/初始化命令），再发送 **0xAC 0x33 0x00**（触发一次测量），80 ms 后读取 6 字节数据。

400 kHz 下实测 SCL 周期约 2.5 μs，地址字节 8 位 + 1 位 ACK 共 9 个时钟，约 22.5 μs；一次 3 字节写事务（含起始、地址、3 数据、停止）约 50 μs 量级。

本实验完成了 uC/OS-III 在 STM32F103C8T6 上的移植，掌握了源码组织、配置裁剪、PendSV/SysTick 对接和 AC6 兼容性处理；通过三个不同周期的任务验证了抢占式调度；完成了 AHT20 的裸机与 RTOS 两种采集实现，并用示波器验证了 I2C 时序。移植过程中遇到的 NVIC 优先级位数、FPU 汇编、AC6 内建函数等问题，加深了对 Cortex-M3 异常模型和编译工具链的理解。
